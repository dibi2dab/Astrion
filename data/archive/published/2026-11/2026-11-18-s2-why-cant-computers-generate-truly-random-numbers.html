Why can't computers generate truly random numbers? A computer is a machine built to follow rules, and a rule that produces the same output from the same input cannot, by itself, produce an unpredictable result. Yet computers shuffle playlists, encrypt messages, and simulate molecular motion. They do it by combining deterministic algorithms with a small amount of genuine physical unpredictability.

6 min read

Key takeaways

  • A pseudorandom generator is a deterministic algorithm; the same seed always produces the same sequence.
  • Pseudorandom output can be excellent for simulations and games but unsafe for cryptography if the seed or algorithm is predictable.
  • Cryptographic generators mix in entropy from hardware events and are designed so that observing past output does not reveal future output.
  • Statistical randomness tests can catch bad generators, but passing them does not prove that a sequence is unpredictable.

Determinism Is the Point

A computer executes instructions. Given the same program, the same inputs, and the same internal state, it produces the same result. That reproducibility is a feature. Debugging, encryption, and scientific simulation all depend on being able to rerun a calculation and get the same answer.

Randomness conflicts with that design. A truly random event has no reproducible cause that the program can inspect. If the program could derive the next number from its current state, an observer who knows the state could derive it too. So a program that only follows deterministic rules cannot create unpredictability out of nothing.

The way out is to change the question. Instead of asking the program to invent randomness internally, feed it a small unpredictable input and let it expand that input into a long sequence. That input is the seed, and the expansion is the pseudorandom generator.

Deterministic does not mean useless

A seeded generator is repeatable by design. That is exactly what a simulation needs when it must reproduce a run, and exactly what a password system must avoid when an attacker can guess the seed.

How a Pseudorandom Generator Works

A simple example is the linear congruential generator. It keeps a state value and updates it with a multiply, an add, and a modulus. The arithmetic is exact, so the sequence is fully determined by the starting value and the constants. Change the constants and you get a different sequence with different statistical properties.

Modern generators are more sophisticated. The Mersenne Twister, a widely used generator, has a very long period and good statistical properties for simulation. Its internal state is large, and its output is designed to avoid short cycles. But it is still deterministic, and its state can be reconstructed from enough output.

The seed is the weak point. If an attacker knows the algorithm and can guess the seed, the entire sequence is predictable. Using the current time as a seed, a practice in older software, is especially weak because the time is often guessable to within a small window.

Where Genuine Entropy Comes From

A true random source measures a physical process that is difficult to predict. Thermal noise in an electronic circuit, the timing of interrupts, radioactive decay, and atmospheric noise have all been used. The key property is not that the process is mysterious. It is that an observer cannot reproduce or anticipate the measurement well enough to predict the output.

Operating systems collect entropy into a pool. Linux exposes it through devices and system calls, and modern hardware often includes a random-number instruction backed by a dedicated circuit. The pool is mixed and stretched so that even a modest amount of physical unpredictability can seed a large amount of output.

A cryptographic generator is designed so that seeing past output does not help predict future output. That property is called forward secrecy or backtracking resistance, depending on the direction. Even if an attacker learns the internal state at one moment, the generator can re-key itself so that earlier or later output remains protected.

Entropy is a resource, not an infinite well. A system that consumes randomness faster than it collects entropy can block, reuse state, or fall back to weaker sources. The engineering problem is to collect enough unpredictability, mix it safely, and never expose the raw state to an attacker.

Why Passing Tests Is Not Enough

Randomness tests look for patterns: bias in bits, repeated subsequences, correlations, and deviations from expected distributions. A bad generator often fails such tests, which makes them useful for quality control. But a test suite is finite, and a cleverly constructed sequence can pass every test while remaining fully predictable.

The distinction matters most in security. A sequence that looks random to a statistician may be trivially reproducible to an attacker who knows the algorithm and the seed. For encryption keys and authentication tokens, the requirement is not cosmetic randomness. It is unpredictability against an adversary.

This is why cryptographic libraries separate concerns. They use a secure generator for secrets, a fast generator for simulations, and a clearly documented entropy source for seeding. Mixing them up can turn a harmless simulation tool into a security hole.

There is also a philosophical point. True randomness may be unavailable or unprovable even in principle. Quantum measurement appears to produce outcomes that are not determined by hidden variables in any locally causal way, and some systems use quantum devices as entropy sources. But for practical computing, the goal is not metaphysical randomness. It is unpredictability that an attacker cannot exploit.

Randomness in Science and Everyday Software

Monte Carlo simulations rely on pseudorandom numbers to sample complicated probability distributions. Reproducibility is valuable there: a researcher can publish a seed and let others recreate the same experiment. The randomness is a computational tool, not a security claim.

Games and procedural graphics use pseudorandom generators to create variation without storing every detail. A seed can regenerate an entire world, which is efficient and convenient. The same property that makes a seed useful for a game makes it dangerous for a password.

Machine learning adds another twist. Random initialization, dropout, and data shuffling all use pseudorandom numbers. Reproducibility depends on controlling seeds and library versions, because different implementations may consume the stream differently. A result that cannot be reproduced is harder to trust.

The practical rule is simple. Use a cryptographic generator when the number protects a secret, and use a seeded generator when you need reproducibility. The computer cannot create randomness from pure logic, but it can stretch a little physical unpredictability into enough numbers for almost any purpose.

Common misconceptions

A computer can generate truly random numbers with the right algorithm.

An algorithm alone is deterministic. It can transform a seed into a long sequence that looks random, but the unpredictability must come from somewhere outside the algorithm, such as a hardware entropy source. The algorithm stretches randomness; it does not create it.

If a sequence passes statistical randomness tests, it is safe for encryption.

Statistical tests check for visible patterns, not for unpredictability against an adversary. A deterministic generator with a guessable seed can pass many tests and still be completely predictable. Cryptographic security requires a generator designed for that threat model.

Using the current time as a seed is random enough.

The current time is often predictable to within seconds or less, so an attacker can try a small range of seeds. Time-based seeding was a common source of real vulnerabilities. Secure systems gather entropy from hardware events and mix it carefully.
